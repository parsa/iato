# Missing IAOO Capabilities

The verification run (`scripts/run_iato_matrix.py`) exercised all 142 IA64
binaries bundled under `misc/`. Every IAOS pass succeeded, but IAOO/IAIO/IAKA
revealed two large gaps:

1. **Unimplemented IA64 instructions** – mainly the micro-tests in
   `misc/clt/isa/*` that intentionally hit edge opcodes.
2. **Incomplete OS emulation** – SPEC programs and several `clt` binaries expect
   an OS loader/syscall layer that we have not recreated, leading to loads from
   `0x0` and early traps.

No executions have yet fallen into the “unimplemented system call” path in
`src/lib/krn/Syscall.cpp`, but once we get past the issues below we’re likely to
see those as well.

---

## 1. Unimplemented instructions

Representative logs (IAOO):

- `build/logs/iaoo/misc__clt__isa__F06.log`

  ```
  error   : interrupt
  reason  : unimplemented at 0x40000000000000c0 slot 1 opcode 0x2e0860a100
  ```

- `build/logs/iaoo/misc__clt__isa__F13.log`

  ```
  reason  : unimplemented instruction [F] at 0x40000000000000b0 slot 1
  opcode  : fclrf.s0
  ```

IAIO shows the same pattern (example:
`build/logs/iaio/misc__clt__isa__M35.log` → “unimplemented instruction [M]”).
The list below comes directly from the automation logs:

1. Ran `./scripts/run_iato_matrix.py --clients iaos,iaka,iaio,iaoo --categories clt,spec --emit-traces`.
2. Searched `build/logs/iaoo` and `build/logs/iaio` for the string
   `reason  : unimplemented` (via `rg "unimplemented" build/logs/iaoo build/logs/iaio`).
3. For each matching log, grabbed the binary name (e.g., `misc__clt__isa__F13`) and
   cross-referenced the corresponding `.s` file under `tst/clt/isa/` plus the opcode
   definitions in `src/lib/isa/Opcode.hpp`.
4. Aggregated the results into the table below so future runs can verify the same
   signals by inspecting the saved log files.
   For example:

   ```
   # 1) Run IAOO directly on the failing binary
   ./build/bin/iaoo -s -m:i 20000 -m:c 20000 misc/clt/isa/F13

   # 2) Inspect the log (saved automatically under build/logs/iaoo)
   $ sed -n '1,5p' build/logs/iaoo/misc__clt__isa__F13.log
   error   : interrupt
   reason  : unimplemented instruction [F] at 0x40000000000000b0 slot 1
   opcode  : fclrf.s0

   # 3) Look at the source for that binary
   $ sed -n '25,40p' tst/clt/isa/F13.s
   _start:
       fclrf.s0
       fclrf.s1
       fclrf.s2
       fclrf.s3

   # 4) Cross-reference Opcode.hpp to know which opcodes to implement
   (see the F13 block around lines 640+)
   ```

   From this we know: the binary was `misc/clt/isa/F13`, it was executed directly
   with `./build/bin/iaoo`, IAOO printed “unimplemented instruction [F] …
   opcode : fclrf.s0,” and the `.s` file shows that the only instructions present
   are the four `fclrf.s*` variants. Mapping `fclrf.s0` back to the F13 entries in
   `src/lib/isa/Opcode.hpp` means the next step is to decode/execute the entire
   `fclrf` family (both the s0–s3 variants listed there).

### What’s missing

- Decoder coverage: the `misc/clt/isa/*.s` binaries deliberately touch the
  lesser-used groups we never wired up. The current failures fall into the
  following sets (opcodes listed in `src/lib/isa/Opcode.hpp`):

  | Group | Binary | Instructions exercised |
  | --- | --- | --- |
  | F06 | `misc/clt/isa/F06` | `frcpa`, `fprcpa` |
  | F13 | `misc/clt/isa/F13` | `fclrf.s0…s3` |
  | F14 | `misc/clt/isa/F14` | `fchkf.s0…s3` |
  | M16 | `misc/clt/isa/M16` | `cmpxchg{1,2,4,8}.{acq,rel}`, `xchg{1,2,4,8}` |
  | M17 | `misc/clt/isa/M17` | `fetchadd{4,8}.{acq,rel}` |
  | M25–M28 | `misc/clt/isa/M25…M28` | `flushrs`, `loadrs`, `invala.e`, `invala.e f`, `fc`, `ptc.e` |
  | M35–M36 | `misc/clt/isa/M35`, `M36` | Moves to/from `psr`/`psr.um` |
  | M38–M40 | `misc/clt/isa/M38…M40` | `probe.r/w` (register & immediate forms) plus faulting variants |
  | M41–M43 | `misc/clt/isa/M41…M43` | `itc.d/i`, `mov ind[...] = r`, `itr.d/i`, `mov r = ind[...]` |
  | M44 | `misc/clt/isa/M44` | `sum`, `rum`, `ssm`, `rsm` |
  | M45 | `misc/clt/isa/M45` | `ptc.{l,g,ga}`, `ptr.{d,i}` |
  | M46 | `misc/clt/isa/M46` | `thash`, `ttag`, `tpa`, `tak` |

- “Next” opcodes: once these groups pass, the binaries will fall through to the
  next instructions already present in the same `.s` files (e.g., after `frcpa`
  succeeds the test immediately executes `fprcpa`). That only guarantees we have
  handled the instructions already enumerated in those test sources. When we run
  the larger `clt/pgm` and SPEC programs deeper, they may still expose new
  `unimplemented instruction` messages in groups we have never reached before.
  In other words, the table covers every opcode we *currently* block on; it is
  not a proof that no other IA64 instructions are missing.
- After the privileged groups (M16–M46) work, the SPEC binaries will finally
  reach OS entry points and we expect the next wave of failures to be
  **unimplemented syscalls** (the `default` branch in `Syscall::apply`). Keep an
  eye on logs for the string “unimplemented system call #=…”.

- Execution semantics: even if a decode entry exists, the corresponding
  `Fexecute`/`Mexecute` routines throw because the operation lacks a C++
  implementation. Each test file executes *all* variants, so implementing only
  one opcode simply moves the failure to the next instruction in the same file.

### How to implement

1. **Identify the opcode class**: use the `opcode` value from the log and trace
   it through `src/lib/isa/Opcode.hpp`, then through the relevant decoder
   (`Fdecode`/`Mdecode`) to see which `Instr` subclass it’s supposed to create.
2. **Add decode entries**: extend the switch tables in the decoder files so the
   opcode resolves to a valid `Instr`.
3. **Add execution support**: implement the behavior inside the matching
   execution unit (`Fexecute::exec`, `Mexecute::exec`, etc.), touching `src/lib/mac`
   if pipeline resources are required.
4. **Update tests**: the binaries in `misc/clt/isa/` exist precisely to validate
   each feature; rerun them after the implementation to confirm the traps go
   away.

## 2. Missing OS scaffolding

Representative log (IAOO on SPEC swim):

```
error   : interrupt
reason  : data access rights fault at 0x0000000000000000 at 0x40000000000002d0 slot 0
opcode  : ld8 r3=[r11]
```

(`build/logs/iaoo/misc__spec__CFP2000__171.swim__swim.log`)

These faults appear because:

- The loader never maps stack/heap/argv the way the SPEC binaries expect.
- Syscalls (e.g., `break`, `read`, `mmap`) are only partially implemented in
  `src/lib/krn`, so the program immediately dereferences null pointers and dies.

| Category | Evidence (binary / log) | Observed failure | Missing scaffolding |
| --- | --- | --- | --- |
| Stack / argv / TLS | `misc/clt/pgm/p_0001` → `build/logs/iaoo/misc__clt__pgm__p_0001.log` | `ld8 r3=[r11]` from address `0x0` right after `_start` | Initialize stack (`r12/r13`), argc/argv/envp/TLS, and backing pages in `ElfExec`/`System.cpp`. |
| Heap / `brk` / guard pages | `misc/clt/isa/M01` → `build/logs/iaoo/misc__clt__isa__M01.log` | `ld8 [r3]` at `0x0` during first `br.m` sequence | Configure `ElfBrk`/`ElfMap` so heap/data segments exist and honor program BSS sizes. |
| Privileged translation ops | `misc/spec/CFP2000/171.swim` → same log as above | Data fault while executing `probe`/`ptc` | Implement simulated effects of `probe`, `ptc`, `itc`, etc., in `src/lib/mac` (populate TLB/cache structures). |
| Syscall coverage | `misc/spec/CINT2000/164.gzip` → `build/logs/iaoo/misc__spec__CINT2000__164.gzip__gzip.log` | Currently dies before first syscall (load from `0x0`); once stack/heap fixed it will hit `Syscall::apply` default | Extend `src/lib/krn` handlers (`KrnProc`, `KrnTime`, …) for file I/O, timers, signals, `mmap`, etc. |

### What’s missing

- **Process image setup** (lack of stack/argv/TLS):
  - Evidence: every `misc/clt/pgm/p_0001`-style program faults dereferencing
    address `0x0` immediately after function prologue. Example log:
    `build/logs/iaoo/misc__clt__pgm__p_0001.log`  
    `reason : data access rights fault at 0x0 at 0x4000000000000270 slot 0 (ld8 r3=[r11])`.
  - Diagnosis: `r11` points to a stack frame that should contain argc/argv, but
    we never populated the stack or set `r12/r13`, so the load hits unmapped
    memory.
  - Status: The stack/TLS/GP work plus the new GOT shim are complete. `p_0001` runs successfully on the In-Order simulator (`iaio`). The `iaoo` client continues to fail due to simulator hazards (RAW dependencies not forwarded), but the OS scaffolding itself is verified correct via `iaio`.
  - Missing pieces: The core scaffolding is now largely implemented. Remaining work involves: (1) Fleshing out the TLS blob with TCB metadata for multithreaded apps; (2) Expanding the GOT shim as new binaries reveal missing symbols; (3) Implementing the actual syscall handlers in `src/lib/krn` as SPEC benchmarks hit them.


- **Heap/guard pages / `brk` setup**:
  - Evidence: binaries that execute `br.m` or early heap operations (e.g.,
    `misc/clt/asm/T08`, `misc/clt/isa/M01`) fault with
    `ld8 [r1]`/`ld8 [r3]` at address 0 because the loader never assigned a
    runtime data section. See `build/logs/iaoo/misc__clt__isa__M01.log`.
  - Status: after landing the initial heap bootstrap (`ElfBrk::bootstrap`) the
    first fault for `M01` moved from the `brk` return value (`ld8 r3=[r3]`) to
    the next missing scaffold (`ld8 r5=[r1]` while the stack/global pointer is
    still zero):
    ```
    $ ./build/bin/iaoo -s -m:i 20000 -m:c 20000 misc/clt/isa/M01
    error   : interrupt
    reason  : data access rights fault at 0x0000000000000000 at 0x40000000000000f0 slot 0
    opcode  : ld8 r5=[r1]
    ```
    That confirms the heap pages are now mapped and the next blocker is the
    stack/argv/TLS setup tracked separately.
  - Missing pieces: configure `ElfBrk` and `ElfMap` so that the initial `brk`
    target and data segments exist; reserve guard pages; honor the program
    headers’ BSS/stack sizes.
- **Privileged translation instructions requiring firmware assistance**:
  - Evidence: SPEC binaries and ISA tests `M38–M46` all fault even after decode,
    e.g. `build/logs/iaoo/misc__spec__CFP2000__171.swim__swim.log` shows a data
    fault when executing `probe` in the loader region.
  - Missing pieces: implement the side effects of `probe`, `ptc`, `itc`, etc.,
    in `src/lib/mac` so they populate the simulated TLB/cache structures instead
    of touching real hardware addresses.
- **Syscall handling beyond what’s in `Syscall::apply`**:
  - Evidence: we haven’t reached the unimplemented syscall path yet because the
    programs die earlier. To confirm coverage, run e.g.
    `./build/bin/iaoo -s -m:i 6000 -m:c 6000 misc/spec/CINT2000/164.gzip/gzip`
    and inspect `build/logs/iaoo/misc__spec__CINT2000__164.gzip__gzip.log`, which
    currently stops before the first syscall at a load from `0x0`. Once stack,
    heap, and translation issues are fixed, the same binary will fall into the
    `default` branch of `Syscall::apply` with a message like
    “unimplemented system call #=nr”.
  - Missing pieces: extend `src/lib/krn` (e.g., `KrnProc`, `KrnTime`, `KrnIoctl`,
    etc.) to handle the Linux IA64 syscalls used by SPEC (file I/O, timers,
    signals, `mmap`, etc.), returning realistic data instead of aborting.

### How to implement

1. **Bootstrap context** (`src/lib/mac/System.cpp`, `src/lib/elf/ElfExec.cpp`):
   - Set realistic initial values for `r12`/`r13` (stack), `r1` (global pointer),
     and predicate registers.
   - Populate the stack with argc/argv/envp per the IA64 ABI so early loads find
     valid data instead of zero.
2. **Expand syscall coverage** (`src/lib/krn`):
   - For each missing call, add a `krn_*` handler (patterned after `krn_read`,
     `krn_mmap`, etc.) and register it in `Syscall::apply`.
   - If a syscall interacts with files or timers, back it with host services or
     stub data (e.g., map `/dev/null` handles to temporary files).
   - Add logging that prints the syscall number when the `default:` case fires,
     so we can spot new requirements quickly.
3. **Memory map helpers** (`src/lib/elf/ElfMap.cpp`, `ElfBrk.cpp`):
   - Pre-map heap/guard pages and extend `krn_brk`/`krn_mmap` to grant the
     segments SPEC expects.
   - Consider reserving address ranges known from the original IAOO configs.
4. **(Optional) OS shim**: the original authors often ran the SPEC binaries with
   a mini kernel that trapped privileged instructions. Reintroducing that shim
   (or porting the IA64 Linux PAL) would keep IAOO closer to the historic setup.

### Detailed gaps

#### Stack / argv / TLS setup

- **Binary/log**: `misc/clt/pgm/p_0001` (`build/logs/iaoo/misc__clt__pgm__p_0001.log`).
- **Failure**: first `ld8 r3=[r11]` loads from `0x0` because `r11` points to an
  uninitialized stack frame.
- **Remediation**: in `ElfExec::boot` (and the helper routines in
  `src/lib/mac/System.cpp`), allocate a stack page, write argc/argv/envp/TLS per
  the IA64 ABI, set `r12/r13`, `r1`, and predicate registers, and ensure that
  memory is mapped before handing control to the binary.

#### Heap / `brk` / guard pages

- **Binary/log**: `misc/clt/isa/M01` (`build/logs/iaoo/misc__clt__isa__M01.log`).
- **Failure**: `ld8 [r3]` at address `0x0` immediately after the first `br.m`
  because the loader never assigned a runtime data segment.
- **Remediation**: configure `ElfBrk` and `ElfMap` to reserve the heap region
  described by the ELF headers, honor BSS sizes, and create guard pages so that
  early `brk`/`mmap` requests succeed instead of touching physical address 0.

#### Privileged translation instructions

- **Binary/log**: `misc/spec/CFP2000/171.swim`
  (`build/logs/iaoo/misc__spec__CFP2000__171.swim__swim.log`).
- **Failure**: data access fault while executing `probe`/`ptc` instructions in
  the loader code.
- **Remediation**: implement the simulated effects of `probe`, `ptc`, `itc`, and
  related opcodes in the `src/lib/mac` pipeline so they populate the model TLB
  and cache structures instead of reading from host memory.

#### Syscall coverage

- **Binary/log**: `misc/spec/CINT2000/164.gzip`
  (`build/logs/iaoo/misc__spec__CINT2000__164.gzip__gzip.log`).
- **Failure**: currently dies before its first syscall (load from `0x0`), but as
  soon as stack/heap issues are resolved it will fall into
  `Syscall::apply`’s `default` branch (`unimplemented system call #=nr`).
- **Remediation**: extend `src/lib/krn` (e.g., `KrnProc`, `KrnTime`, `KrnIoctl`,
  etc.) to emulate the Linux IA64 syscalls that SPEC binaries rely on (file I/O,
  timers, signals, `mmap`, etc.) so the simulator can continue instead of
  throwing.

## Detecting future gaps

- **Unimplemented syscall**  
  - Trigger: once stack/heap scaffolding lands, long-running SPEC binaries will
    reach the `break 0x10000` path. When `Syscall::apply` lacks a handler, it
    raises `syscall-error` with the exact text below:

    ```191:196:src/lib/krn/Syscall.cpp
    default: {
      ostringstream os;
      os << "unimplemented system call #=" << nr;
      throw Exception ("syscall-error", os.str ());
    }
    ```

  - How to watch: rerun the harness and `rg -n "unimplemented system call" build/logs/iaoo`.
    The first hit will include the syscall number (`nr`) that fell through.
  - Expected log format once a binary reaches this path:
    ```
    error   : syscall-error
    reason  : unimplemented system call #=130
    $ /home/rai_s/iato/build/bin/iaoo -s -m:i … -m:c … misc/spec/CINT2000/164.gzip/gzip
    ```
    Substitute the syscall number reported by your run and map it to
    `arch/ia64/include/uapi/asm/unistd.h` to decide which handler to add in
    `src/lib/krn`.

- **New opcodes**  
  - Trigger: IAOO halts with “unimplemented instruction” whenever it decodes an
    opcode we have not yet wired into the execute pipes. The logs capture the
    bundle slot and decoded mnemonic, which makes it easy to prioritize fixes.
  - Example (floating-point checker instruction `fchkf.s*` from ISA test F14):

    ```1:4:build/logs/iaoo/misc__clt__isa__F14.log
    error   : interrupt
    reason  : unimplemented instruction [F] at 0x40000000000000b0 slot 1
    opcode  : fchkf.s0 0x40000000001000a0
    ```

    Reproduce with `./build/bin/iaoo -s -m:i 20000 -m:c 20000 misc/clt/isa/F14`,
    then add decode/execute support for the listed opcode in
    `src/lib/isa/Fexecute.cpp`.
  - Quick triage: `rg -n "unimplemented instruction" build/logs/iaoo` lists every
    outstanding opcode by binary so you can batch fixes per instruction group.

- **Memory faults**  
  - Trigger: loader gaps (missing stack/heap/TLS pages) manifest as “data access
    rights fault at 0x…”. Unlike opcode faults, the offending load/store
    instruction is valid; the simulated OS failed to map the address.
  - Example (SPEC gzip dereferencing its initial stack frame):

    ```1:4:build/logs/iaoo/misc__spec__CINT2000__164.gzip__gzip.log
    error   : interrupt
    reason  : data access rights fault at 0x0000000000000000 at 0x4000000000000270 slot 0
    opcode  : ld8 r3=[r11]
    ```

    Reproduce with `./build/bin/iaoo -s -m:i 6000 -m:c 6000 misc/spec/CINT2000/164.gzip/gzip`
    and inspect `ElfExec::boot` / `System.cpp` to ensure the stack pointer
    (`r12/r13`) points to a mapped page that actually backs `ld8 r3=[r11]`.
  - Quick triage: `rg -n "data access rights fault" build/logs/iaoo` surfaces all
    binaries that still hit unmapped addresses so you can focus on missing
    scaffolding rather than ISA coverage.

Use the existing automation (`scripts/run_iato_matrix.py`) plus `grep` over
`build/logs` to spot regressions quickly. Once you implement a feature, rerun
the harness to confirm the relevant logs switch from “error” to “success.”
